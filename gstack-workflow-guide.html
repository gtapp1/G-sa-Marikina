Ideation & Planning

Before writing any code, validate your idea, define scope, and lock in the technical and design plan. These skills feed into each other sequentially — each one refines the output of the previous.

STEP 1

/office-hours — Validate the Idea

Start here. Two modes available: Startup mode asks six forcing questions that expose demand reality, status quo alternatives, and your narrowest wedge. Builder mode runs design-thinking brainstorming for side projects or hackathons. Either way, it produces a design doc that feeds everything downstream.

Output: Design document with validated problem statement and approach
STEP 2

/plan-ceo-review — Stress-Test Ambition

CEO/founder-mode review of your plan. Rethink the problem, find the 10-star product, challenge premises. Four modes: Scope Expansion (dream big), Selective Expansion (hold scope + cherry-pick), Hold Scope (maximum rigor), Scope Reduction (strip to essentials). Ensures you're building the right thing at the right ambition level.

Output: Refined product vision with locked scope decision
STEP 3

/plan-design-review — UI/UX Plan Review

Designer's-eye review of the plan's UI/UX dimensions. Rates each design axis 0-10, explains what would make it a 10, then fixes the plan to get there. Catches usability issues, accessibility gaps, and interaction design flaws before any pixels are placed.

Output: Plan updated with design improvements and scores
STEP 4

/plan-eng-review — Engineering Review

Eng-manager mode. Lock in the execution plan — architecture, data flow, diagrams, edge cases, test coverage, performance considerations. Walks through issues interactively with opinionated recommendations. This is your last chance to catch structural mistakes before implementation.

Output: Architecture diagram, data flow, edge case coverage, test plan
STEP 5

/plan-devex-review — Developer Experience Review

Use if your platform has developer-facing features (APIs, SDKs, CLIs, docs). Explores developer personas, benchmarks against competitors, designs magical moments, traces friction points. Three modes: DX Expansion, DX Polish, DX Triage.

Output: DX scorecard with actionable improvements

💡 Shortcut: Auto-Review

Use /autoplan to run all planning reviews (CEO, Design, Eng, DX) sequentially with auto-decisions. One command, fully reviewed plan out. Best when you trust the defaults and want speed.

2

Design System & Visual Direction

With a validated and reviewed plan, define your visual identity and produce production-ready markup. These skills build on each other: system → exploration → finalization.

STEP 6

/design-consultation — Define the Design System

Understands your product, researches the landscape, and proposes a complete design system: aesthetic direction, typography, color palette, layout grid, spacing scale, and motion principles. Creates DESIGN.md as your project's single source of truth for all visual decisions.

Output: DESIGN.md with complete design system specification
STEP 7

/design-shotgun — Explore Visual Variants

Generate multiple AI design variants for key pages and components. Opens a comparison board for side-by-side evaluation. Collect structured feedback and iterate until you find the right direction. Great for landing pages, dashboards, and complex UI flows.

Output: Approved design direction with feedback annotations
STEP 8

/design-html — Finalize as Production HTML/CSS

Takes approved mockups from /design-shotgun, CEO plans, or design review context and generates production-quality HTML/CSS. Text actually reflows, heights are computed, layouts are dynamic. 30KB overhead, zero dependencies. Smart API routing picks the right patterns for each design type.

Output: Production-ready HTML/CSS files
3

Implementation

Time to build. Break features into precise specs, scope your edits, debug systematically, and monitor code health as you go. This phase is a repeatable loop — run it for each feature or module.

STEP 9

/spec — Turn Features into Executable Specs

Transforms vague intent into a precise, executable specification in five phases. Files a GitHub issue, optionally spawns a Claude Code agent in a fresh worktree for parallel development. Each spec becomes a trackable, shippable unit of work.

Output: GitHub issue with detailed spec, optional worktree agent
STEP 10

/freeze — Scope Your Edits

Restrict file edits to a specific directory for the session. Blocks writes outside the allowed path. Prevents accidentally modifying unrelated modules while focused on one feature. Use /unfreeze when you're ready to widen scope again.

Output: Edit guardrail active for the session
STEP 11

/investigate — Systematic Debugging

When you hit bugs, don't guess. This skill enforces four phases: investigate → analyze → hypothesize → implement. The iron law: no fixes without root cause. Use whenever you encounter errors, 500s, stack traces, or "it was working yesterday" scenarios.

Output: Root cause identified, targeted fix applied
STEP 12

/health — Monitor Code Quality

Run periodically during development. Wraps your project's type checker, linter, test runner, dead code detector, and shell linter. Computes a weighted composite 0-10 score and tracks trends over time so you can catch quality drift early.

Output: Quality score with trend data

💡 Context Management

Use /context-save before ending a session and /context-restore when resuming. Captures git state, decisions made, and remaining work so you never lose momentum across sessions.

4

QA & Polish

Before shipping, verify everything works correctly and looks right. These skills test functionality, visual consistency, and developer experience on the live application.

STEP 13

/qa — Functional QA & Bug Fixing

Systematically tests your web app, finds bugs, fixes them in source code (committing each fix atomically), and re-verifies. Three tiers: Quick (critical/high only), Standard (+ medium), Exhaustive (+ cosmetic). Produces before/after health scores and a ship-readiness summary. Use /qa-only for report-only mode without fixes.

Output: Bug fixes committed, ship-readiness report
STEP 14

/design-review — Visual QA

Designer's-eye QA on the live site. Finds visual inconsistencies, spacing issues, hierarchy problems, AI slop patterns, and slow interactions. Then iteratively fixes them in source code, committing each fix and re-verifying with before/after screenshots.

Output: Visual fixes committed with screenshot evidence
STEP 15

/devex-review — Live DX Audit

For developer-facing platforms. Actually navigates your docs, tries the getting-started flow, times TTHW (Time To Hello World), screenshots error messages, evaluates CLI help text. Compares against /plan-devex-review scores to find plan-vs-reality gaps.

Output: DX scorecard with evidence and boomerang comparison
STEP 15b

/benchmark — Performance Baseline

Establish baselines for page load times, Core Web Vitals, and resource sizes. Compare before/after on every PR. Tracks performance trends over time so regressions are caught immediately.

Output: Performance baseline with trend tracking
5

Ship & Monitor

Code is ready, QA passed. Now review the diff, ship it safely, monitor production, and update documentation to match what actually shipped.

STEP 16

/review — Pre-Landing PR Review

Analyzes your diff against the base branch for SQL safety issues, LLM trust boundary violations, conditional side effects, and other structural problems. Catches the things linters miss. Run this before every merge.

Output: Structured review with issue severity and fix suggestions
STEP 17

/cso — Security Audit

Chief Security Officer mode. Covers secrets archaeology, dependency supply chain, CI/CD pipeline security, LLM/AI security, OWASP Top 10, and STRIDE threat modeling. Two modes: Daily (zero-noise, 8/10 confidence gate) and Comprehensive (monthly deep scan). Essential before shipping auth, payments, or sensitive data handling.

Output: Security report with findings and remediation steps
STEP 18

/ship — Create the PR

The ship workflow: detects and merges base branch, runs tests, reviews diff, bumps VERSION, updates CHANGELOG, commits, pushes, and creates a PR. One command from "code is ready" to "PR is open."

Output: PR created with version bump and changelog
STEP 19

/land-and-deploy — Merge & Verify

Takes over after /ship creates the PR. Merges, waits for CI, waits for deploy, then verifies production health via canary checks. The final step from PR to live.

Output: Code live in production, health verified
STEP 20

/canary — Post-Deploy Monitoring

Watches the live app for console errors, performance regressions, and page failures using periodic screenshots. Compares against pre-deploy baselines and alerts on anomalies. Keep this running for the first hour after deploy.

Output: Continuous monitoring with anomaly alerts
STEP 21

/document-release — Sync Documentation

Reads all project docs, cross-references the diff, builds a Diataxis coverage map, updates README/ARCHITECTURE/CONTRIBUTING/CLAUDE.md to match what shipped. Detects architecture diagram drift, polishes CHANGELOG voice, and surfaces documentation debt.

Output: All documentation synced to reflect shipped code

Ongoing & Maintenance

Skills you'll use throughout the project lifecycle — not tied to a specific phase but valuable at any point.

RECURRING

/retro — Weekly Retrospective

Analyzes commit history, work patterns, and code quality metrics with persistent history and trend tracking. Team-aware: breaks down per-person contributions with praise and growth areas. Run at the end of each sprint or work week.

RECURRING

/learn — Manage Project Learnings

Review, search, prune, and export what gstack has learned across sessions. Useful when you wonder "didn't we fix this before?" or want to understand accumulated project patterns.

AS NEEDED

/document-generate — Write Missing Docs

Generate documentation from scratch for a feature or module. Uses the Diataxis framework (tutorial / how-to / reference / explanation) to produce complete, structured documentation.

AS NEEDED

/diagram — Generate Architecture Diagrams

Turn English descriptions into diagram triplets: Mermaid source, editable .excalidraw file, and rendered SVG + PNG. Fully offline. Great for documenting architecture decisions or explaining flows to teammates.

SAFETY

/guard — Full Safety Mode

Combines /careful (warns before destructive commands) with /freeze (blocks edits outside a directory). Use when touching production, debugging live systems, or working in shared environments.

UTILITY

/landing-report — Queue Dashboard

Shows which VERSION slots are claimed by open PRs, which workspaces have WIP work likely to ship soon, and what slot /ship would pick next. Read-only snapshot for coordination.
